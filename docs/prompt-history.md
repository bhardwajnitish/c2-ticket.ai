## 002 — Logical architecture

**File:** [.specstory/history/002-logical-architecture.md](../.specstory/history/002-logical-architecture.md)  
**Date:** 2026-11-19  
**Deliverable:** [spec/architecture.md](../spec/architecture.md)

Using only spec/requirements.md, design the logical architecture of c2-ticket.ai. Do not write code. Save spec/architecture.md.

One Spring Boot process hosts everything. No microservices.

Components and trust rules:
- API boundary validates request shape and returns ticket results, a grounded answer, or an explicit no-match
- Ticket application service orchestrates persistence
- State machine is the only authority for from → to; the UI hiding a button is not sufficient
- Ticket store is PostgreSQL
- Ingestion refreshes vectors as a consequence of a successful ticket change, not as an optional client call
- Retriever embeds the query, fetches top-K, then applies the similarity threshold
- Grounding gate: empty keep-set stops the pipeline and emits no-match; the generator is not called
- Generator receives only retrieved chunk text
- Citations are assembled from the keep-set, not parsed out of free-form model text
- top-K and threshold come from configuration

Document the status-change flow, the ticket-data-change flow, and the RAG query flow. Leave auth, tenancy, and the embedding vendor as open until later specs. Do not invent paths, schemas, or field lists that are not in the requirements.

**Date:** 2026-11-19  
**Deliverable:** [spec/data-model.md](../spec/data-model.md)

Design the data model for c2-ticket.ai before any JPA entities. Do not write code. Save spec/data-model.md.

Decisions (lock these; do not leave them open):

Ticket fields: id (internal surrogate), ticketId, title, description, priority, status, assignee, category, resolutionNotes, createdAt, updatedAt.
- ticketId is generated by the backend. Pattern TKT-1001, TKT-1002, … regex ^TKT-[0-9]+$. It is the public business key. Clients never send it.
- status enum: OPEN, IN_PROGRESS, RESOLVED, CLOSED, CANCELLED. New tickets start OPEN.
- priority enum: LOW, MEDIUM, HIGH. Default MEDIUM when omitted.
- title required, max 255. description and resolutionNotes optional, max 10000.

Comment fields: id (UUID), ticketId, author, content, createdAt.
- Many comments belong to one ticket. A comment cannot exist without its ticket.

Indexes required for filtering: unique ticketId; status; priority; assignee; category; status + createdAt.

RAG chunk metadata copied from the ticket at ingest: ticketId, status, priority, assignee, category, plus content, chunk index, content fingerprint, embedding model, chunker version, ingestedAt.

Also record what is still open: auth, pagination, delete, whether CLOSED/CANCELLED tickets stay in the corpus.

## 006 — RAG ingestion specification

**File:** [.specstory/history/006-rag-ingestion.md](../.specstory/history/006-rag-ingestion.md)  
**Date:** 2026-11-19  
**Deliverable:** [spec/rag-ingestion.md](../spec/rag-ingestion.md)

Using spec/requirements.md, spec/architecture.md, and spec/data-model.md, write the RAG ingestion specification for c2-ticket.ai. Do not write Java. Save spec/rag-ingestion.md.

Lock these decisions:

1. Internal pipeline only. Clients cannot be the sync mechanism.
2. Run synchronously after the ticket/comment transaction commits. A failed ingest does not roll back the ticket. On embedding failure, log it and leave the previous vectors unchanged.
3. Knowledge document template, omitting blank sections:
   Title
   Description
   Comments (one line each, chronological)
   Resolution notes
4. Chunking is section-based with fixed-size overflow (ING-D-5):
   - sections: title+description, each comment, resolution notes
   - if the whole document fits in rag.chunk.max-characters (default 2000), emit one chunk
   - otherwise split oversized sections with overlap-characters (default 250)
   - every chunk starts with: [Ticket {ticketId}] {title}\n
   - chunker version: section-v1
   - max-tokens and overlap-tokens may exist in config but the chunker uses characters
5. Fingerprint content + metadata + chunker version + embedding model. Skip rewrite when the fingerprint is unchanged.
6. Dev embeddings: local Ollama, model nomic-embed-text, dimension 768, http://localhost:11434. Same model for ingest and query. Cloud embeddings are an optional production alternative, not the dev path.
7. Vector store: PGVector in the same PostgreSQL database. Table ticket_chunk, embedding vector(768), cosine distance operator <=>, similarity s = 1 - distance, HNSW index with vector_cosine_ops.
8. Replace semantics: delete all chunks for that ticketId, then insert the new set, in one unit of work. No usable content deletes existing vectors.
9. Re-ingest on create, field update, comment add, and status change.
10. Retrieval config via @ConfigurationProperties prefix rag.retrieval:
    - top-k default 5
    - similarity-threshold default 0.72
    RagRetrievalService receives the properties by constructor. It must not hardcode 5 or 0.72. Order is top-K first, then threshold.

## 007 — RAG query API contract

**File:** [.specstory/history/007-rag-api-contract.md](../.specstory/history/007-rag-api-contract.md)  
**Date:** 2026-11-19  
**Deliverable:** [spec/rag-api-contract.md](../spec/rag-api-contract.md)

Design the stable JSON contract the c2-ticket.ai backend promises to the frontend. Do not write code. Save spec/rag-api-contract.md.

Endpoint: POST /api/v1/rag/query
Request: { "query": string }, required, trimmed, reject blank with 400.

Response envelope: every key is always present. Unused keys are null.
{
  "outcome": "ANSWER" | "NO_MATCH" | "ERROR",
  "query": string,
  "answer": { "text": string } | null,
  "citations": [ { "ticketId": "TKT-…", "title": "…" } ],
  "confidence": { "score": number, "basis": "RETRIEVAL" } | null,
  "escalation": { "recommended": boolean, "reason": string | null } | null,
  "error": { "code": string, "message": string } | null,
  "noMatch": { "code": string, "message": string } | null
}

Rules:
- Empty keep-set → HTTP 200, outcome NO_MATCH, answer null, citations [], confidence null, escalation.recommended true, reason and noMatch.code NO_RELEVANT_TICKETS. Do not call the LLM.
- ANSWER citations come only from the keep-set, one per ticketId, ordered by descending similarity then ascending ticketId. Title is loaded from the ticket store. confidence.score is the best keep-set similarity.
- Infrastructure failures (embedding, vector store, generation) are outcome ERROR, not NO_MATCH.
- A post-generation gate that fails (ticket id in the answer text that is not in the keep-set, or a duration claim that contradicts context) downgrades to NO_MATCH. Do not return a guessed ANSWER.

Add section 8.1 and treat this text as normative generator instructions, copied verbatim into the prompt:

Answer the user's question using only the supplied ticket context.
Do not use general knowledge to answer support-specific questions.
If the supplied context does not contain enough information to answer the question, explicitly state that no relevant tickets were found.
Do not invent ticket IDs, events, causes, resolutions, users, or dates.
Every factual claim about a ticket must be supported by the retrieved ticket context.

## 008 — REST API contract (tickets & comments)

**File:** [.specstory/history/008-api-contract.md](../.specstory/history/008-api-contract.md)  
**Date:** 2026-11-19  
**Deliverable:** [spec/api-contract.md](../spec/api-contract.md)

Write spec/api-contract.md for c2-ticket.ai. Do not write code. Stay consistent with spec/data-model.md and spec/state-machine.md.

Base path /api/v1. JSON, camelCase. No auth in v1. No pagination in v1. No delete.

Endpoints:
- POST /tickets — create. Body: title (required), description, priority, assignee, category. Reject client ticketId or status with 400. Server sets ticketId and status OPEN. Priority defaults to MEDIUM. Response 201 with the ticket.
- GET /tickets — list. Optional query filters only: status, priority, assignee, category. No keyword parameter. Combine with AND. Return the full matching array.
- GET /tickets/{ticketId} — 200 or 404 TICKET_NOT_FOUND.
- PATCH /tickets/{ticketId} — partial update of title, description, priority, assignee, category, resolutionNotes. status is forbidden on this endpoint.
- PATCH /tickets/{ticketId}/status — body { "status": TicketStatus }. 400 INVALID_STATUS_TRANSITION when the policy rejects it.
- POST /tickets/{ticketId}/comments — body author, content. 201. Comment id is a UUID string.
- GET /tickets/{ticketId}/comments — chronological list.

Error envelope for all of these:
{ "error": { "code": string, "message": string, "details": [ { "field": string, "message": string } ] } }
Validation errors use VALIDATION_ERROR. Unknown JSON properties fail.

Ticket JSON fields: ticketId, title, description, priority, status, assignee, category, resolutionNotes, createdAt, updatedAt. Do not expose the internal numeric id.
